# 运维、发布与历史演练

## 发布流程

1. 执行 `make release-check`，确认测试、格式、静态检查和配置检查通过。
2. 确认 migration 已审核，且新旧版本可在同一 schema 上运行。
3. 先金丝雀发布，观察健康检查、错误率、延迟、队列与业务指标。
4. 异常时停止扩容并回滚应用；数据库仅执行已验证的兼容性恢复步骤。

## 常见告警

| 告警 | 首要动作 |
| --- | --- |
| 服务不可用 | 检查 `/livez`、注册中心、依赖连通性和最近发布。 |
| 错误率或延迟上升 | 按接口、依赖和版本拆分指标，检查熔断与限流。 |
| Outbox/死信积压 | 暂停风险写入，检查消费者、幂等与重试原因。 |
| 支付回调/退款异常 | 校验签名、重放、订单状态与对账结果。 |
| NATS 不可用或注销事件积压 | 保持 Outbox 数据不变，检查 NATS 连通性、Stream、消费者与重试状态；不要手动标记已发布。 |

## 历史演练摘要

2026-07 的 Review 与平台金丝雀/回滚演练，以及 schema 兼容性验证，均确认了“先验证兼容性、再小流量发布、最后扩容”的流程。日期记录仅作为证据，不替代当前发布检查；每次发布必须重新执行本章流程并记录结果。

## 韧性演练记录模板

每次演练都应在变更记录系统中保留独立记录；本模板不代表演练已经发生。

| 项目 | 记录内容 |
| --- | --- |
| 基本信息 | 日期与时区、执行人/复核人、环境、变更单和演练场景。 |
| 前置检查 | `make gmicro-resilience-check` 通过，告警、错误率、延迟和注册中心状态正常。 |
| 下线实例 | 预期 `/readyz` 失败、实例被摘流；记录 Consul 状态、错误率和延迟。 |
| 恢复实例 | 预期实例重新就绪、注册并逐步恢复流量；记录注册数、P95 和错误率。 |
| 依赖延迟 | 预期超时、限流或熔断按配置生效；记录依赖延迟、熔断与降级指标。 |
| 停止与回滚 | 写明停止阈值、删除 Chaos Mesh 资源、恢复实例和健康检查确认结果。 |
| 后续 | 记录结论、问题、负责人和截止日期。 |
